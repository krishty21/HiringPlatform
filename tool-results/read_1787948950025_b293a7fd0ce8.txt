    25→    25→SECTION 3 — NON-NEGOTIABLE OPERATING PRINCIPLES
    26→    26→====================================================================
    27→    27→
    28→    28→1. FREEZE CONTRACTS FIRST. Database schema, TypeScript types, zod schemas, API route signatures, and the shared component contract are built in Phase 0 and treated as frozen interfaces. Parallel workstreams consume them; they do not redefine them. If a contract must change mid-build, only the Orchestrator changes it, updates all consumers, and logs it in DECISIONS.md.
    29→    29→2. WORKING SOFTWARE EVERY PHASE. At the end of every gate (G0–G5, mirroring SRD §12), the app must compile (next build passes, tsc --noEmit clean, eslint clean) and the features built so far must actually work. Never leave the repository in a broken state, ever.
    30→    30→3. GRACEFUL DEGRADATION OVER HARD FAILURE. You may not have real API keys for LLM providers, and you cannot receive magic-link emails. Design for this from the start: an AI abstraction layer with a deterministic mock provider as default, and a demo-mode login path (Section 12). The app must be 100% functional with ZERO third-party API keys configured.
    31→    31→4. SECURITY BY DEFAULT, NOT BY PATCH. Row Level Security on every table from the first migration, zod validation on every input boundary, role guards in middleware, private storage for documents, PII minimization per SRD §10 and VER-06. Security is part of the definition of done for every module, not a cleanup task.
    32→    32→5. NO PLACEHOLDER ROT. No "TODO: implement", no lorem ipsum, no hardcoded fake JSON pretending to be a database call. Every screen shows real data from the database. Empty states are real, designed empty states (an intentional UX pattern), not missing features.
    33→    33→6. LOG EVERYTHING. DECISIONS.md records every non-obvious choice with a one-line rationale. EXPLANATION_LOG.md records, per module, a 5-line plain explanation, one edge case, and one key file — this is a graded deliverable (hackathon FAQ requires the team to explain the code, so make every module explainable in plain language).
    34→    34→7. TIMEBOX AND MOVE. If a single problem resists you after 3 serious attempts, implement the simplest working fallback, log it in DECISIONS.md with the label FALLBACK, and continue. A working 90% solution beats a broken 100% attempt. Perfectionism is applied only where the SRD's acceptance criteria demand it.
